# 更新 stock-master 的标准流程

本文件是 **meta 工作流**——指导 agent 怎么补全 / 修正 / 扩展本 skill 本身。

触发场景：
- 用户说"优化 skill"、"这个 skill 缺什么"、"能不能补一个 XX 功能"
- agent 跑工作流时发现脚本 / 模板 / 数据缺位
- 行情 / 监管 / 板块结构变化（北交所规则调整、新板块出现）
- 新数据源接入

## 原则（先读后写）

1. **最小化改动** —— 只改真正缺的东西，不重写整个 skill
2. **向后兼容** —— 老工作流 / 脚本继续能跑，新参数默认行为不变
3. **一个入口** —— 新数据源走 `scripts/clients/`，不要在 workflow 里直连 fetcher
4. **不写会变的东西** —— 字段号、版本号、具体价位一律不进文档
5. **不改 frontmatter name / description** —— 这两个是触发器

## 缺口 → 落点

| 缺口类型 | 落到哪里 |
|---|---|
| 数据抓取（API / 接口） | `scripts/fetchers/<source>.py`，并在 `scripts/clients/__init__.py` 暴露 |
| 分析算法（指标 / 评分 / 估值） | `scripts/analysis/<algo>.py` |
| 筛选策略（门槛 / 评分） | `scripts/screening/<pool>.py` |
| 输出导出（Markdown / Excel） | `scripts/export/<format>.py` |
| 工作流说明（步骤 / 决策树） | `references/workflows/<场景>.md` |
| 输出模板 | `references/templates/<场景>-card.md` |
| 静态规则 / 硬阈值 | `references/data/<主题>.md` |
| 验证过的新数据源清单 | `SKILL.md`「数据源实测状态」表 |

## 标准更新流程

### Step 1：明确缺口

- 缺什么？**功能 / 数据源 / 模板 / 规则 / 工作流**？
- 谁会用？**所有工作流** 还是 **特定场景**？
- 现有能拼凑吗？还是必须新建？

### Step 2：归类落点

按上表分到对应目录，命名保持一致。

### Step 3：写代码 / 文档

- 脚本只依赖标准库 + 已验证依赖（numpy/pandas/curl_cffi/akshare/openpyxl）
- 出错打 `WARN` 日志，**不吞异常**
- 返回值保持 dict，新字段向后兼容（老调用方忽略即可）

### Step 4：更新索引

- 新工作流 → 更新 `references/workflows/README.md`
- 新模板 → 更新 `SKILL.md` 输出模板表
- 新静态规则 → 更新 `references/workflows/README.md` 配套规则清单

### Step 5：验证

```sh
cd /var/minis/skills/stock-master
python3 scripts/_selftest.py --quick       # 60 项全链路（--quick 跳过 22 项慢用例），退出码非 0 即不可交付
python3 scripts/_probe_actions.py          # 动了取数 / 编排相关代码时再跑（出网，串行约 10s）
```

- 老脚本仍能跑（向后兼容）
- 报错信息可读，不抛 raw traceback
- 新增公开接口要**加进 `_selftest.py`**，否则下次坏了没人知道

### Step 6：沉淀

**会重犯的错** → `shared/_system/lessons/YYYY-MM-DD-<主题>.md`（≤ 800 字符）
**决策记录** → 写进本文件末尾「决策记录」，只写**为什么**和**当前状态**，
不写版本号、不写"从 X 改成 Y"的对比。

## 决策记录

### 2026-10-11 — 归并 short-stock-screener / limit-up-trader

**决定**：两个独立 skill 取消，内容并入 stock-master。

**原因**：
- 三个 skill 的短选规则（市值门槛、止损、权限过滤）互相冲突，用户看到三份不同答案
- 每日流程实际是「先看盘 → 再决定稳健还是进攻」，拆成三个 skill 反而要来回切
- 触发词重叠严重（"涨停战法"同时命中两个 skill）

**做法**：
- 稳健短线 → `workflows/short-screen.md`
- 打板 → `workflows/limit-up.md`（互斥，同一时段只跑一个）
- 共用数据层抽到 `scripts/clients/`
- 命令行工具 `scripts/short_tool.py` 为唯一行情/筛选入口

**代价**：每次跑短选多读一个文件；触发词收敛后 description 变长。

### 2026-10-11 — 数据层收口到 clients

**决定**：workflow 文档不再直接调 `fetchers.*`，统一走 `scripts/clients`。

**原因**：同一个"拿行情"在 5 个 workflow 里有 5 种写法，某个 fetcher 挂了要改 5 处；
且各处对「北向 status=3」的处理不一致（有的当 0）。

**做法**：`clients` 内统一异常处理、统一缺失值语义（`unavailable` 而非 `0`）、
统一多源 fallback 顺序。

### 2026-10-11 — 规则冲突收敛（用户逐条裁定）

**决定**：把散落在三个 skill / 多个文档里的冲突口径统一，以用户裁定为准。

| 项 | 最终口径 |
|---|---|
| 市值门槛 | 流通市值 **≥ 50 亿，无上限**（删除 300 亿上限） |
| 持有周期 | 短线 **1-5 个交易日**（T+1）；中线 3-6 月；长线 6-18 月 |
| 止损 | 全 skill **统一 -7%**（含中线 / 财报场景 / 打板） |
| 仓位 | 短选单票 ≤10%/持仓 ≤3；打板单票 ≤5%/持仓 ≤2/日总仓 ≤10% |
| 板块 | 硬过滤 300/301/688/8/920/ST/B 股 + 重组风险股 |
| 科技排除 | **取消**（半导体/算力/创新药等不再整体排除） |
| 竞价策略 | 短选 >5% 不追（稳健）与打板 5-9.5% 可挂（进攻）**互斥**，不得混用 |
| 账户基准 | 文档不出现具体总资金数字 |

**评分量纲**：保留两套但显式区分 —— `score_short` 为技术面 0-100（短选门槛 ≥60），
`score_general` 为 100 分制综合分（技术 60 + 消息 30 + 宏观 10），研报/卡片用后者。

**原因**：用户在不同时间给过互相矛盾的规则，且三份文档各自演化，导致同一只股票
在不同工作流下得到不同结论。冲突不收敛，skill 越大越不可信。

### 2026-10-11 — K 线跨度静默截断（**影响所有长周期指标**）

**症状**：`xueqiu.kline(code, count=250)` 恒返回 58 条；MA60 全为 `null`，
长周期趋势判定与「年线支撑」类结论全部失效，且**不报错**。

**原因**：雪球 kline 接口的实际返回条数由 `begin` 时间戳决定，`count` 只是上限。
旧实现把 `begin` 固定写死为 90 个自然日 —— 90 天只够约 58 个交易日，
所以不管 `count` 传多少，最多只能拿到 58 条。

**修复**：按周期反推自然日跨度（day ×1.6 / week ×9.8 / month ×39），
并在自检里加断言「请求 250 条必须拿到 ≥ 250 条」。

**教训**：`count` / `limit` 这类参数**不能假定服务端会照办**。
凡「取 N 条」的接口，都要断言**实得条数**，否则下游指标会静默失真。

### 2026-10-11 — 自检脚本（`_selftest.py` / `_probe_actions.py`）

**决定**：脚本改动后必须能一条命令验证。

**原因**：本轮流沙盒里出现过多次「函数名对不上 / 入参签名变了 / 返回字段名变了」
这类只有真跑才暴露的问题（如 `quote_batch` 悬空引用、`pool_selector` 中线池入参
类型不匹配、`news_scorer` 把"业绩预亏"判成看多），静态检查全查不出来。

**做法**：`_selftest.py` 覆盖日历/行情/涨停池/可买性/clients/fetchers/分析/
筛选/风险/情绪/研报共 60 项，含正负例断言；`_probe_actions.py` 串行探活编排层全部动作（雪球对并发敏感，并发会报假失败）。
新增公开接口一律补进自检。
